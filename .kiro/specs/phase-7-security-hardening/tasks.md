# Implementation Plan: Phase 7 — Security Hardening

## Overview

This plan implements Phase 7 across four codebases: `court-booking-common` (shared `PiiSanitizationFilter` Logback turbo-filter and SECURITY_ALERT DTO additions), `court-booking-platform-service` (security event consumer, REST APIs for security alerts/IP blocklist/auto-responses, scraping detection, progressive rate limiting, brute-force/suspicious-login detection, retention/anonymization jobs, secret rotation hooks, Stripe Connect security monitoring, input validation hardening), `court-booking-transaction-service` (full role-based JWT enforcement replacing the no-op `SecurityConfig`, JWKS caching, IP blocklist filter, booking/payment/payout/self-booking fraud detection, ChargebackRateEvaluationJob, WebSocket interceptors), `court-booking-admin-web` (security alerts dashboard, IP blocklist page, auto-response config page, CSP build-time wiring, security WebSocket hook), and `court-booking-infrastructure` (NGINX security headers/CORS/IP allowlists, Istio PeerAuthentication, encryption-at-rest verification). Tasks are ordered so each builds on the previous: schema migrations and shared library code first, then per-service detection/response logic, then infrastructure and admin UI, then property/integration/smoke tests. Phase 7 strictly **extends** Phase 1b (security tables), Phase 2 (`JwtAuthenticationFilter`, `RateLimitFilter`, `JwksController`), Phase 4 (Stripe webhook handling), Phase 5 (WebSocket auth on `/ws?token=...`), and Phase 6a (`CsrfValidationFilter`, `CsrfTokenController`, `ApiRateLimitFilter`); existing components are wired/extended, not recreated. Every acceptance criterion across the 29 Phase 7 requirements is traceable to at least one task, and the 30 correctness properties enumerated in `design.md` are mapped to optional property-based test tasks.
